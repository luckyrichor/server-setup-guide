# 第二跳告警延迟与恢复确认（2026-10-27）

## 当前行为

- 正式探测仍每30秒触发；执行耗时、锁和systemd调度会使实际间隔有所不同。
- 主站使用ifconfig.me/ip；curl28（超时）、35（TLS）或56（接收失败）时，同轮最多一次访问ipinfo.io/ip。两个站点都必须按活动路由经过Webshare，返回有效且符合expected_ip的出口；复核预算最多10秒。主站正常不额外复核；错误出口、错误模式、无可验证路由仍失败。
- 最终检测失败立即加载AppArmor门禁、清理当前Claude CLI及可识别子进程；常驻guard持续清理新进程，不等待通知阈值。
- 首次失败记failure_started_at。故障未解除且本轮仍失败，经过至少90秒后的下一轮才诊断并排队发送一次故障通知。诊断、发送或调度耗时可能使通知晚于90秒。
- 连续两次正式探测成功后，才将有效healthy状态设为true并解除门禁。第一次成功仍保持拦截和清理；期间再失败，成功计数归零。
- 未进入告警阶段的短故障只留本机日志，不发故障/恢复消息。已告警故障恢复时发一次恢复通知；此前任务不自动重启。
- 通知发送失败保留队列，故障消息始终在对应恢复消息之前，使用原幂等ID重试。因此飞书不可达时，可能在网络恢复后收到延迟送达的故障及恢复消息。
- 旧版本持久化incident按已经告警迁移，避免漏掉既有故障的恢复消息。初次启动健康不发送恢复通知。

## 配置

私有配置`/etc/claude-webshare-watch/config.json`：

```json
{
  "fallback_probe_url": "https://ipinfo.io/ip",
  "alert_delay_seconds": 90,
  "recovery_successes": 2
}
```

默认延迟90秒、连续成功2次。主站预算仍20秒、连接8秒；服务总预算105秒。更换备用站点时须先验证活动规则确实走Webshare，不能使用只走第一跳的api.ipify.org冒充第二跳复核。通知目标继续使用现有群配置。

## 验证与边界

32项自动化测试通过，覆盖延迟边界、短故障静默、连续恢复/中断、持续清理、下一故障计时重置、通知失败顺序/幂等、门禁错误和旧状态迁移；旧测试以显式0秒/1次配置保持原兼容场景覆盖。包含仅对测试sleep进程的真实终止测试。

现场只读演练：在内存中将主站返回模拟为curl35，实际访问备用ipinfo.io/ip，经活动规则与出口IP验证通过。未制造生产断网、未杀真实Claude任务、未发送演练群消息。新版生产timer的健康结果和源码hash由部署记录核对。

分段诊断仍可能无法证明具体物理故障点；本次没有将“诊断路径未确认”误当成网络故障根因，也没有调整Clash模式或名单。
