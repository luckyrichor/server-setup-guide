# 个人偏好

## 新项目的默认工作位置

- 当用户要求创建一个全新项目时（不限于“做一个新项目”，任何意思相近的表述均算，如“新建项目”“帮我搭一个 XXX”“开个新工程”等），默认在 `/Users/USERNAME/Project/` 下新建一个子文件夹作为该项目的根文件夹，并在其中进行所有操作。
- 创建该项目根文件夹前，必须先征得用户同意，以确认创建路径；同意后方可创建，未经同意不得创建。此确认仅针对项目根文件夹这一次。
- 根文件夹创建后，内部后续操作按 Agent 通常的工作方式进行即可；例如敏感操作酌情询问，非敏感操作直接执行，无需逐一确认。
- 子文件夹名取简洁、有意义的名字；确认路径时可一并确认名字。
- 本规则仅适用于新建项目；已有项目或当前目录下的零散任务不适用，按当前工作目录正常操作。
- 若 `/Users/USERNAME/Project/` 不存在，先创建它，再创建项目根文件夹。

## 回复语言

- 与用户交流时，尽量使用中文回复。

## 个人信息位置

- 用户的个人信息及详细介绍存放在 `/Users/USERNAME/Project/个人信息/` 文件夹中（概括见其中的 `个人信息简介.md`，各子目录为详细材料）。需要时可从该位置读取，此处不记录具体内容。

## 项目文档交付要求

当用户在开发项目过程中要求提供产品文档或技术文档时，除非用户明确指定其他形式，否则遵循以下要求：

### 产品文档

- 产品文档不能只有纯文字描述，必须同时提供可视化页面或可直接查看的可视化成果。
- 可视化成果应根据项目类型呈现核心页面、界面布局、用户操作流程、页面跳转关系和关键交互状态。
- 默认优先提供可在浏览器中直接打开的页面、原型或高保真界面；如果项目本身没有图形界面，则应提供与产品形态相适应的流程图、架构视图、状态视图或其他可视化表达。
- 可视化内容必须与产品文档中的需求、功能和流程保持一致，不能仅作为无实际对应关系的示意图。
- 交付时应明确说明可视化成果的文件路径、打开方式和查看入口。

### 技术文档

- 技术文档应尽可能完整、具体，达到开发人员可以据此理解、实现、联调、测试和维护系统的程度。
- 内容应根据项目实际情况覆盖：技术架构、模块划分、核心流程、数据模型、数据库设计、接口设计、依赖关系、配置项、权限与安全、异常处理、日志与监控、测试方案、部署方式以及维护注意事项。
- 涉及接口时，应逐项说明接口用途、请求方式、路径、认证方式、请求参数、参数类型、是否必填、约束条件、请求示例、响应字段、响应示例、状态码、错误码和异常场景。
- 涉及内部模块、服务、事件、消息队列、回调或第三方系统时，也应说明调用关系、输入输出、时序、失败处理、重试策略、幂等要求和兼容性约束。
- 对尚未确定的内容，必须明确标注待确认项、假设条件和潜在风险，不能把推测写成已经确定的事实。

## 项目交接文档(AGENTS.md + CLAUDE.md)维护要求

目的:任何开发任务或项目,无论做完还是只做了一部分,都要让另一个从未参与过的
agent(或人)只读这份文档,就能弄清项目是什么、做到哪了、怎么继续,无需翻聊天记录。

### 文件组织
- 在项目根目录同时维护 `AGENTS.md` 和 `CLAUDE.md` 两个文件,目的是让 Claude Code
  和其他 AI 工具(Codex、Cursor、Gemini CLI 等)都能自动读到同一份交接信息。
- **`AGENTS.md` 是唯一的正文**:下文"应包含的内容"全部写在 `AGENTS.md` 里。
- **`CLAUDE.md` 只做引用**:内容以一行 `@AGENTS.md` 开头(Claude Code 会自动导入
  该文件),其后只写仅适用于 Claude Code 的补充说明(没有就不写)。不要在两个文件里
  重复维护同一份内容,避免两边不一致。
- 两个文件不存在就新建;已存在则在原有内容基础上更新,保留他人写的内容,不整篇覆盖。
  如果项目里只有一份已写好正文的 `CLAUDE.md`,把正文迁移到 `AGENTS.md`,
  再把 `CLAUDE.md` 改成上述引用形式。
- 下文中提到的"交接文档"均指 `AGENTS.md`。

### 何时写 / 更新
- 每完成一个有意义的阶段(一个功能、一次修复、一轮重构、一个里程碑)后立即更新,
  不要等到整个项目结束。
- 以下情况也必须更新:任务中途停止或被打断、准备交接给其他 agent / 会话、
  做出了重要的技术决策或方案变更、发现了新的坑或已知问题。
- 每次结束一轮工作、向用户汇报"完成"之前,先确认 AGENTS.md 和飞书开发记录都已同步到最新状态。
- 零散的一次性小任务(问答、单个脚本、临时查询)不需要。

### 应包含的内容(按项目实际情况取舍,宁详勿略)
1. **项目概述**:项目是什么、解决什么问题、目标用户、核心功能范围(做什么 / 不做什么)。
2. **技术栈与环境**:语言、框架、主要依赖及版本、运行环境要求、需要的环境变量
   或配置项(只写变量名和用途,不写密钥真实值)。
3. **快速上手**:安装依赖、本地启动、运行测试、构建、部署的具体命令,能直接复制执行。
4. **目录结构**:关键目录和文件各自的职责,入口文件在哪。
5. **架构与核心流程**:模块划分、模块之间如何调用、数据如何流动、关键数据模型。
   复杂内容可放到 `docs/` 下单独成文,在此处链接。
6. **关键决策记录**:做过哪些重要选择、为什么这样选、放弃了哪些方案及原因。
7. **当前进度**(最重要,必须具体):
   - 已完成:列出已完成的功能 / 模块,以及是否经过验证(怎么验证的)。
   - 进行中:正在做什么、做到哪一步、改动了哪些文件、还差什么。
   - 未开始:计划中但还没动的部分。
8. **下一步计划**:接手者应该先做什么,按优先级排列,每条尽量具体到可以直接开工。
9. **已知问题与坑**:未修复的 bug、临时绕过的方案(workaround)及原因、容易踩的坑、
   环境上的特殊注意事项。
10. **约定与规范**:代码风格、命名、分支 / 提交规范、测试要求等本项目特有的约定。
11. **待确认事项**:需要用户决定或尚未确定的问题、当前采用的假设。
12. **更新日志**:按时间倒序简要记录每次更新(日期 + 做了什么),日期使用绝对日期。

### 写作原则
- 写给"完全没有上下文的人"看:不要用"刚才那个问题""上面说的方案"这类依赖对话的指代。
- 只写确认过的事实;未验证的内容明确标注"未验证 / 推测",不能把推测写成结论。
- 保持准确优先于保持简短:过时的内容要改掉或删掉,而不是只在末尾不断追加,
  确保"当前进度"一节始终反映真实最新状态。
- 涉及具体代码时写清文件路径(必要时带行号 / 函数名),方便直接定位。
- 不写入任何密钥、密码、token 等敏感信息。

### 同步到飞书文档
每次更新交接文档（`AGENTS.md`）时，同一份进展也要同步记录到用户飞书「我的文档库」中。
项目里的文档给接手的 agent 看，飞书文档留给用户本人查阅，两边都要有记录。
本节是对「飞书文档」一节的补充：署名、`--as user`、先列后建、写后回查等规定照常适用。

**放在哪里(沿用文档库现有结构,2026-10-24 核对)**
- 每个项目一个目录节点,节点名用项目名。已有的直接复用,例如顶层的 `ExampleProjectA`、`ExampleProjectB`,
  以及 `ExamplePlans` 下的各项目(`example-platform`、`example-memory` 等)。
- 新项目在文档库顶层新建一个同名节点;如果项目属于 `ExamplePlans` 的计划或实验,就建在 `ExamplePlans` 下。
  拿不准归属时先问用户。
- 写入前先 `wiki +node-list` 查一遍现有结构,不要凭记忆判断。

**写什么**
- **开发记录**(必有):每个项目一篇,标题为「<项目名> 开发记录」。每次同步时在文末**追加**一节,内容包括:
  - 标题:日期 + 本次做了什么
  - 改动内容和涉及的文件
  - 验证方式和结果(未验证的写明"未验证")
  - 代码版本(仓库名@短哈希,规则同署名)
  - 当前进度、下一步、遗留问题
  - 每节第一行写一行简短署名(谁写的、日期),因为同一篇会由不同助手追加
  篇幅过长时,新建「<项目名> 开发记录(二)」,并在旧篇末尾追加一行指向新篇的说明。
- **方案 / 版本文档**(按需):技术方案、设计、发布说明等成体系的内容单独成篇,沿用现有命名习惯,
  例如「<项目名> 技术方案 v1」「<项目名> 0.6.0:……」。
- 首次同步一个项目时,先写一篇「<项目名> 项目概览」,内容取自 `AGENTS.md`(项目概述、技术栈、架构、当前进度)。

**只新增,不改旧内容**
- 已写入的内容原则上不修改、不删除。
- 同一件事有变化时,二选一:
  1. 在原文档末尾追加一节"更新(日期)",说明改了什么、为什么改;
  2. 新建一篇新版本文档(v1 → v2 → v3),在新版开头注明它替代哪一版、主要变化是什么。
- 旧内容写错了,也用追加"更正(日期)"的方式说明,不回头改原文。只有用户明确要求时才修改已有内容。

**确认方式**
- 某个项目**第一次**往飞书写入时,按「飞书文档」一节的要求,先把目录位置、要新建的节点和文档标题告诉用户,
  等用户确认。
- 用户确认过之后,往同一项目目录里追加开发记录、新建新版本文档都属于已确认的范围,不用每次再问。
  但每次写完都要回查位置,并把文档链接告诉用户。

**其他**
- 在项目的 `AGENTS.md` 里记下该项目的飞书目录和各文档链接,方便下一个 agent 找到。
- 不写入任何密钥、密码、token 等敏感信息;涉及内部地址或个人信息时只写必要内容。
- 本机无法写飞书时(未安装 `lark-cli`、没有对应 profile 或授权失效),照常更新项目文档,
  并在 `AGENTS.md` 里标注"飞书待同步:<日期> <内容>",同时告诉用户。之后由能写飞书的机器或 agent 补写,
  补写完成后删除这条标注。

## Claude 与 Codex 协作分工

### 协作模式（只有这两种）
- **Claude 主导，Codex 执行**：Claude 负责派活、指导和验收。具体实施可以交给 Codex，也可以由 Claude 亲自完成任意部分，由 Claude 视情况安排。
- **Codex 自己主导并执行**：由 Codex 独立完成，不涉及 Claude。
- **不存在"Codex 主导、Claude 执行"的方式。** Codex 主导的任务不要交给 Claude 去做。

### 分工边界：前端由 Claude 亲自完成
- 前后端都有的任务，后端可以按本节规定交给 Codex 执行，**前端必须由 Claude 亲自完成，不交给 Codex**。
- **判断原则：凡是用户能看到的东西，都算前端。** 常见的包括但不限于：
  - 网页：页面、组件、样式、交互效果
  - 移动端 App：例如安卓、iOS 应用的页面和界面
  - 桌面端应用：例如 Mac App、Windows 客户端里展示给用户的软件页面
  - 游戏：界面、菜单、HUD 等 UI，以及角色模型、场景、特效、动画等画面上呈现的内容
  - 其他形态的产品，只要是用户看得到的部分，同样适用
- 前端以外的部分，比如接口、数据库、网络通信、数据处理、算法、游戏规则逻辑、构建和部署脚本，**可以交给 Codex，也可以由 Claude 自己做**，由 Claude 视情况决定。这条规则只限定"前端不交给 Codex"，并不意味着前端以外的部分只能由 Codex 做。
- **边界拿不准时，不自行决定**：先告诉用户这部分是什么、为什么拿不准，由用户决定由谁来做。
- Codex 执行后端任务时，如果发现需要改动前端才能完成，比如接口变了、页面也要跟着调整，不要自己动前端，而是在交回时说明需要前端配合改什么，由 Claude 完成。
- 本条适用于 Claude 主导的任务。Codex 自己主导并执行的任务，按 Codex 自己的安排进行。

### 适用范围
- 只在装有 Codex CLI 的机器上这样做（目前是 Mac 和 tx）。没有 Codex CLI 的机器上，由 Claude 自己完成。
- 任务不一定有方案：
  - **小事**：不需要写方案，Claude 可以直接做，也可以交给 Codex 做。
  - **有方案的任务**：方案一定是用户和 Claude 讨论出来的，必须写成文档放在用户能看到的地方（项目的 `docs/` 下），并按「同步到飞书文档」的规则同步到飞书。方案定下来之后才开始执行。
- 交给 Codex 时，在当前和用户沟通的地方（对话窗口或飞书会话）通知一句，例如"这部分由 Codex 来做，我负责验收"。**这只是告知，不用等用户同意，发完就可以开始。**

### 用户关注的重点
- 用户一般关注两头：开始前的方案或打算怎么做，结束时的结果是否达到要求。
- 中间过程（怎么派活、执行说明怎么写、和 Codex 来回几轮）由 Claude 自行安排，平时不必逐一汇报。
- 但这不是绝对的：
  - 用户问起中间过程时，如实、具体地说明；
  - 遇到需要用户决定的问题（见下文第 4 种处理方式）时，主动找用户；
  - 进展明显偏离预期（例如耗时远超预估）时，主动告知。

### 执行说明
- 执行说明怎么写由 Claude 决定，不用给用户看。小事可以直接在交给 Codex 的指令里说清楚；有方案的任务，执行说明以方案为依据，补充执行层面的细节：本次范围、不能动的文件、分阶段步骤、每个阶段的验收标准和检查命令。
- **存放位置**：放在**该项目根目录**下的 `.agent-tasks/`，一个项目一个。
  - "项目"指一个独立的项目文件夹，通常就是一个 git 仓库。例如 tx 上 `~/project/ExamplePlans` 本身不是项目，它下面的 `example-platform`、`example-memory`、`planning-docs` 等才是，各自有自己的 `.agent-tasks/`。跨项目、总计划层面的任务放在 `planning-docs/.agent-tasks/`。
  - 只在某个项目真正派活时才创建，不预先给每个项目都建。
  - 第一次创建时把 `.agent-tasks/` 加进该项目的 `.git/info/exclude`（只在本机生效，不改项目共享的 `.gitignore`），确保不会被提交。非 git 项目同样放在 `.agent-tasks/`。
  - 不放 `/tmp` 等临时目录：会被系统清理，耗时记录也会随之丢失，接手的 agent 也看不到。也不要散落在项目根目录、用户主目录或其他无关位置。
- **文件规则**：
  - 一个任务一份文件，文件名为 `日期-任务名.md`，例如 `2026-10-24-登录接口改造.md`。同一个任务即使分多个阶段、来回多轮，也一直用同一份文件。
  - 新任务新建文件；原任务的方案被推翻重来时，新建一份并在文件名后加 `-v2`、`-v3`，开头注明替代了哪一份。
  - **指令部分**（目标、范围、各阶段步骤、验收标准）可以修改，始终保持为当前最新要求，让 Codex 按最新版本执行。每次修改都在"修订记录"里追加一行：时间、改了什么、为什么改。
  - **记录部分**（修订记录、耗时记录、问题记录）只追加，不修改、不删除。
  - 任务完成后文件保留，不删除。用户想清理时由用户决定。

### 耗时记录
每份执行说明末尾放两张表，用于事后排查哪个环节慢。平时不需要专门去看。

**耗时记录**：按时间顺序记录每个事件，标明属于第几阶段。

| 时间 | 阶段 | 谁 | 事件 | 结果/备注 |
|---|---|---|---|---|
| 10-24 09:00:05 | — | Claude | 写完执行说明，派活 | 共 5 个阶段 |
| 10-24 09:01:12 | 阶段1 | Codex | 开始 | |
| 10-24 09:35:40 | 阶段1 | Codex | 交回 | 卡住，见问题 #1 |
| 10-24 09:36:00 | 阶段1 | Claude | 上报用户 | 问题 #1 需要用户决定 |
| 10-24 10:10:22 | 阶段1 | 用户 | 做出决定 | 选方案 B |
| 10-24 10:40:15 | 阶段1 | Codex | 交回 | 完成 |
| 10-24 10:48:30 | 阶段1 | Claude | 验收结论 | 通过 |

**问题记录**：每个问题一条，用编号和耗时记录对应起来。

| 编号 | 阶段 | 发现时间 | 问题描述 | 已尝试 | 处理方式 | 解决时间 |
|---|---|---|---|---|---|---|
| #1 | 阶段1 | 09:35:40 | 数据库迁移和现有表结构冲突 | Codex 试了 3 次 | 第 4 种：用户决定 | 10:40:15 |

- 事件类型：派活、开始、交回（完成或卡住）、Claude 处理问题、上报用户、用户决定、返工（第几轮）、验收开始、验收结论。Claude 和 Codex 各记自己负责的事件，用户的决定由 Claude 代记。
- 时间必须用 `date '+%m-%d %H:%M:%S'` 现场读取，**不允许凭印象写，也不要由 agent 估算"花了多久"**，耗时一律由相邻时间戳相减得出。
- 只在事件发生时记一行，不记琐碎的小步骤。
- 需要更细的排查（例如具体哪条命令慢）时，再结合 Codex（`~/.codex/sessions/`）和 Claude Code（`~/.claude/projects/`）自带的会话记录，那里有毫秒级时间戳。

### Codex 执行时（写给 Codex 看）
- 严格按 Claude 的执行说明和对应的方案执行，不擅自扩大范围，不改说明之外的文件。
- 每个阶段完成后交回给 Claude 验收，验收通过后再进入下一阶段（执行说明另有安排的除外）。
- 遇到问题先自己排查。同一个问题尝试三次仍没解决，或者需要偏离方案时，停下来，把卡在哪、试过什么、报错信息交回给 Claude，并在问题记录里登记。
- 交回时汇报：改了哪些文件、怎么验证的、结果如何、有没有遗留问题。
- 按上文要求在耗时记录里记下自己的事件。
- 不自行提交或推送代码，不做删除、覆盖等难以撤销的操作。这些等 Claude 验收后，按用户的要求处理。

### Codex 出问题时（由 Claude 判断用哪种方式）
1. 补充说明，让 Codex 继续做；
2. Claude 修正卡住的部分，剩下的仍交给 Codex；
3. 问题复杂或反复失败时，Claude 接手自己完成；
4. **需要用户来定**：Codex 解决不了，Claude 也遇到难以取舍的问题，例如要偏离已定的方案、有几种做法各有利弊、影响范围或成本超出预期。这时 Claude 要把问题、可选做法和各自的影响告诉用户，等用户决定，再按用户定的做法交给 Codex 或自己完成。哪些问题属于这一类，由 Claude 判断。

### Claude 验收，并向用户报告结果
- 不以 Codex 的汇报为准。Claude 要亲自查看改动内容，运行测试和检查命令，逐条对照方案或任务要求。
- 不通过的话，退回 Codex 修改，或者 Claude 自己修正，直到达标。
- 最后向用户报告结果：是否达到要求、怎么验证的、遗留问题。同时写进项目的 `AGENTS.md` 和飞书开发记录，注明哪些是 Codex 做的、哪些是 Claude 改的。

## 飞书文档

本机的 `lark-channel` bridge 让 agent 能**以用户本人的身份**创建飞书文档。
因此每一次写入都是替用户对外产出，规矩比写仓库文件严得多。

本机已配置 `codex` 和 `claude` 两个 profile（`~/.lark-channel/profiles/<profile>`），分别对应飞书机器人「Mac Codex 助手」和「Mac Claude 助手」；两者用户授权的权限范围相同（2026-10-24 核对，159 项）。

### 一、每次写入的固定三步

产出重要内容（技术方案、设计取舍、评审、总结这类）时，除了写进仓库，还要**主动提出**整理为飞书文档，用户确认后再建。仓库内的日常记录（`docs/progress.md`、`AGENTS.md`、排期表等）不在此列，照常直接写。

**1. 写入前：说清楚以下几件事，等用户明确确认**

- **标题**
- **大纲 / 内容范围**（有哪些章节）
- **具体目录** —— 落在哪个节点下，以及**需要新建哪几层**
- **使用身份** —— 以用户本人身份（`--as user`）及所用 profile

创建、修改文档或补充署名前都要先确认。理由：文档以用户本人身份创建，未经确认就发出去，等于替用户做了外发决定。**授权登录不等于授权发布。**
用户确认该方案后，一并完成建目录和写文档，不重复索要同一范围的批准。

**2. 定位置：先复用，再新建**

- 按项目、主题或文档类型选择合适的目录；**优先复用已有的合适目录**，同类文档集中归档，不要平行开新目录，也不要把文档散放在「我的文档库」根目录
- 先 `wiki +node-list` 看现有层级，确认没有合适的，**再建目录节点，然后把文档建进去**
- 顺序是**先目录后文档**，不要先建文档再搬

**3. 写入后：核对归档位置，并给出链接**

建完**必须回查确认它真的落在目标节点下**（`wiki +node-list --parent-node-token <目标>`），不能只看创建命令返回 `ok: true`。移动类操作是异步任务，更要确认 `status_msg`。

然后把**最终链接及所属目录**交给用户 —— 移动过的文档要给移动后的新链接。

### 二、统一放「我的文档库」，不要放飞书云盘

飞书有两套不同的系统，别混（这里的"云盘"指飞书自己的云空间，不是 iCloud 等其他网盘）：

| | 我的空间（飞书云盘 / Drive） | **我的文档库（个人知识库 / Wiki）** |
|---|---|---|
| 结构 | 文件夹树 | **节点树**，每个节点是一篇 docx |
| 链接 | `/docx/<token>` | `/wiki/<node_token>` |
| token | 一个 | **两个**：`node_token`（节点）+ `obj_token`（底层文档） |
| 命令域 | `drive` | `wiki` |

**文档统一建在「我的文档库」**（`--space-id my_library`，2026-09-22 用户确认）。飞书云盘只留文件类产物：导出的 PDF、截图、上传的附件。

⚠️ **知识库里没有纯文件夹** —— 本文所说的"目录"都是当目录用的节点，它本身也是一篇（空）docx，靠嵌套形成层级。

⚠️ 很多 `drive` 命令**不认 wiki 链接**，会报 `not exist`；需要底层资源时先 `drive +inspect` 解包成 `obj_token`。

层级**按实际内容设计**，不要套固定模板 —— 项目类的按项目分，跨项目的归一个汇总层，其他类型（学习笔记、会议、调研……）该怎么分就怎么分。目录名简洁清晰（例如「项目名/技术文档」「连接与功能测试」），避免无必要的多层嵌套。**拿不准就在确认环节一起问用户。**

**只建当前用得上的层级**，不要预先把空节点铺开 —— 知识库里的空节点就是一篇空文档，建一堆是噪声。

每次**先列再建**（`wiki +node-list`），已存在就复用，不要造出两个同名节点。

### 三、署名：区分是谁写的

Claude 和 Codex 写出来的文档作者都是用户本人，界面上分不出来，所以**正文第一行必须是**（纯文字，按实际执行的助手二选一）：

```markdown
> 🤖 由 Claude Code 生成 · YYYY-MM-DD · 来源 仓库名@实际提交短哈希 · 工具 lark-cli profile claude
> 🤖 由 Codex 生成 · YYYY-MM-DD · 来源 仓库名@实际提交短哈希 · 工具 lark-cli profile codex
```

- 日期为实际生成日期（北京时间）；工具 / profile 必须反映实际使用的配置。
- 来源仓库与提交哈希必须核对实际分析的代码版本；测试数量、耗时及其他技术结论须对应该版本。**核实过的提交哈希不能省** —— 没有它，文档过两周就无法判断是否已经过期。
- 存在未提交修改时明确标注；提交哈希未经核实时不写哈希，只写仓库名；不得编造或照抄示例哈希。
- 内容不来自代码仓库时（如会议纪要、调研、学习笔记、讨论出的方案），来源直接写明内容出处，例如「来源 基于 2026-10-24 与用户讨论的部署方案」。
- 更新已有文档时保留原始创建来源，注明本次执行助手、日期、代码版本及变更范围，不能将另一助手的原作误标为自己生成。

### 四、身份与凭据

- 以用户本人身份操作时显式使用 `--as user`（作者才是用户本人；`--as bot` 作者是机器人），事先核对实际应用、profile 和授权，不用机器人身份替代。
- **Claude 用 `claude` profile，Codex 用 `codex` profile，不混用凭据。**
- 用户授权（`auth login`）与策略开关（`config strict-mode`）**属于用户自己的操作，agent 不得代劳**。

### 五、操作要点（命令于 2026-09-22 在 tx 服务器实测；本机路径于 2026-10-24 核对）

```bash
# 本机 lark-cli 位于 /opt/homebrew/bin/lark-cli
# <profile> 按实际执行的助手取 claude 或 codex
export LARKSUITE_CLI_CONFIG_DIR=$HOME/.lark-channel/profiles/<profile>/lark-cli/lark-channel

# 先看现有层级（--space-id my_library 只在 --as user 下有效）
lark-cli wiki +node-list --space-id my_library --as user
lark-cli wiki +node-list --space-id my_library --parent-node-token <父节点> --as user

# 需要新层级时建节点（当目录用）
lark-cli wiki +node-create --space-id my_library --parent-node-token <父> \
  --title "<名字>" --obj-type docx --as user

# 文档一次建到位：--parent-token 收 wiki node_token
lark-cli docs +create --as user --parent-token <目标节点token> \
  --title "<标题>" --content @./f.md --doc-format markdown

# 已经建错位置（建到飞书云盘了）才用这个，异步任务要确认 status_msg
lark-cli wiki +move --obj-token <docx token> --obj-type docx \
  --target-space-id my_library --target-parent-token <目标节点> --as user
```

- `LARKSUITE_CLI_CONFIG_DIR` 不指到 profile 目录会报 `not configured`
- `--content @file` **只接受 cwd 下的相对路径**，绝对路径报 `unsafe file path`；用完清理
- **用 `--parent-token` 直接建到目标节点**，不要先建在别处再搬：搬运是异步任务还要确认结果，白白多一个失败点
- `--space-id my_library` 是**按用户解析的别名，只在 `--as user` 下有效**


# Android 手机连接与调试（跨项目规则）

## Mac 连接 Android：先区分 USB、MTP 和 ADB

- 用户说手机已经连接时，不能仅凭 `adb devices -l` 为空，就断言手机未连接、数据线损坏或 USB 调试关闭。分别核对 USB 枚举、DroidMac 的文件访问、ADB 调试。
- 普通文件读取优先使用 DroidMac。选中手机后点击 Refresh；曾经先显示 `No Storage Found`，刷新后立即出现内部存储及 DCIM、Download、Documents。MTP 可用与 ADB 可用是两个独立结论。
- 2026-10-06 已验证：REDMI K80 的 USB 枚举和 DroidMac 文件读取正常，但 ADB 列表为空。保持 DroidMac 运行，切换 ADB 为 libusb 后端并重启服务端，立即恢复为已授权的 `device`。
- 在 USB 已枚举但 ADB 未识别时，先确认没有正在进行的安装或调试任务，再尝试：

  ```bash
  /Users/USERNAME/Library/Android/sdk/platform-tools/adb kill-server
  ADB_LIBUSB=1 /Users/USERNAME/Library/Android/sdk/platform-tools/adb start-server
  /Users/USERNAME/Library/Android/sdk/platform-tools/adb devices -l
  ```

- `ADB_LIBUSB=1` 必须用于启动服务端；仅给后续客户端设置该变量不能切换已有服务端。服务端以后重启时，应重新检查连接，不能把本次恢复当成永久配置。
- 本次证据能确认电脑端 ADB 识别状态异常，切换后端并重启有效；两步同时执行，尚不能区分究竟是 USB 后端兼容性还是旧进程状态所致。不要编造更具体的驱动根因，也不要推断必须退出 DroidMac。
- 只有返回 `unauthorized` 时才提示手机授权；确实无 USB 枚举时再排查线、拓展坞和端口。

## 安装与私有配置

- 修改或安装前，重新核对手机当前包名、版本和安装时间，不能用旧源码版本覆盖手机的新版本。
- 不同包名不共享私有配置；卸载或换包名可能丢失原应用的服务器访问凭据。不能把凭据写进 APK、Git 或聊天记录。


## 本机大模型 API 凭据

- 本台 Mac 已配置火山云 Ark 与腾讯云 TokenHub 密钥，统一保存在 当前用户的 macOS login 钥匙串。
- 新建或维护任何需要大模型 API 的项目时，先读取 `/Users/USERNAME/.config/llm-api/README.md`，使用 `/Users/USERNAME/.local/bin/llm-api ark|tokenhub|both -- COMMAND ...` 向进程注入 `ARK_API_KEY` / `TOKENHUB_API_KEY`，无需再次索要密钥。遵守项目指定的服务商和模型。
- 密钥不得明文写入代码、Git、文档、前端或日志，也不得输出到聊天。API 地址和模型 ID 在实际接入时核实；本机钥匙串不等于远程服务器可用。
